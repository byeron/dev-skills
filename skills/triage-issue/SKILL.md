# triage-issues

`issues/` 内の古くなった issue を棚卸しし、**破棄するかどうか**を判断するスキル。定期的に実行して、古い issue が残り続けるのを防ぐ。

> issue の管理方法（`issues/` の構造、ステータスの遷移、編集ルール）は `agent-issues` に従う。

## 基本方針

- **判断の材料は Claude が集め、決めるのは人間**: 破棄・完了扱い・継続の推奨は Claude が根拠つきで出す。実際にステータスを変えるのは、人間が確認した後だけ。
- **ファイルは消さない**: 破棄は、ステータスを `discarded` にして理由を記録するだけ。ファイルの削除や移動はしない（番号の重複と履歴の喪失を避けるため）。
- **読み取り専用で調査する**: 調査でソースコードや設定は変更しない。変更してよいのは、確認後の issue ファイルのステータスと履歴のみ。
- **根拠を示す**: 推奨の理由には、確認した事実（コマンドと結果、`path:行番号`）を添える。確認できていないものは「推測」と明記する。

## ステータス

ステータスの定義・遷移・権限は agent-issues に従う。このスキルは、人間の確認後に、`discarded`（破棄）と `done`（完了扱い）への変更を行う。

このスキルの対象は、`open` / `needs-info` / `ready` / `approved` の issue。`done` と `discarded` は対象外。

## 手順

### 1. 対象と基準を決める

- 今日の日付を確認する（`date +%Y-%m-%d`）。
- 「古い」の基準は、AGENTS.md に規定があればそれに従う。なければ**最終更新から 30 日以上**とする。ユーザーが期間を指定したらそれを使う。
- 各 issue の最終更新日は、変更履歴・レビュー履歴の最新日付、なければ作成日、さらに `git log -1 --format=%cs -- <issue ファイル>` を参考に決める。
- `issues/` の全ファイルからメタ情報（ID、種別、ステータス、作成日、ブランチ）を読み取り、一覧にする。

### 2. 調査する候補を決める

次のいずれかに当てはまる issue を調査する。

- 最終更新から基準日数以上が経過している
- ステータスが滞留している（例: `approved` なのにブランチが作られていない、`ready` のままレビューされていない、`needs-info` のまま回答がない）
- ユーザーが特定の issue や全件を指定した

候補が 0 件なら、その旨を報告して終了する。

### 3. 候補ごとに調査する（読み取り専用）

次の観点で確認し、事実を記録する。

- **解決済みか**: issue に対応するブランチやコミットが存在し、base にマージ済みか（`git branch -a --list '*<番号>*'`、`git branch --merged`、`git log --all --oneline --grep='#<番号>'`）。bug は再現コマンドや既存テストで今も再現するか。feature はすでに実装されているか。
- **対象が残っているか**: issue の「関連」や「実装手順」に書かれたファイル・関数・設定が、今も存在するか（`ls`、`grep`）。対象のコードが削除・置換されていないか。
- **重複・置き換えがないか**: `issues/` 内に同じ内容、または内容を包含する新しい issue がないか。
- **前提が変わっていないか**: 依存ライブラリ、方針、仕様が変わり、issue の前提が成り立たなくなっていないか。関連ファイルの最近の変更（`git log --since=<日付> -- <ファイル>`）で確認する。
- **進行中の作業がないか**: 対応するブランチに最近のコミットがないか。

調査は issue の判断に必要な範囲にとどめる。

### 4. 判断する

候補ごとに、次のいずれかの推奨を決める。

| 推奨 | 条件 | 適用後 |
|------|------|--------|
| 破棄 | 対象が消えた、前提が変わった、他の issue と重複・置き換えられた、などで、もう実施する意味がない | `discarded` |
| 完了扱い | すでに解決済み（マージ済みの PR や、現状のコードで要件が満たされている） | `done` |
| 要更新 | 問題は有効だが、記載内容（ファイルパス、行番号、方針）が現状とずれている | 変更しない（`polish-issue` で更新を提案） |
| 継続 | 問題が今も有効で、記載も現状に合っている | 変更しない（確認済みとして履歴に記録） |
| 要判断 | 有効かもしれないが、価値や優先度の判断が必要で、事実だけでは決められない | 人間の判断を待つ |

迷う場合は、破棄ではなく「継続」か「要判断」にする。

### 5. 人間に確認する

結果を一覧で提示し、確認を求める。

```
## issue の棚卸し結果（{日付}・基準: 最終更新から{N}日以上）

調査対象: {件数} 件 / 全 {件数} 件

| ID | タイトル | ステータス | 最終更新 | 推奨 | 理由（要約） |
|----|----------|------------|----------|------|--------------|
| 0003 | … | open | 2026-08-01 | 破棄 | 対象の関数が削除済み（path:行） |

### 根拠の詳細
- 0003: {確認したコマンドと結果、ファイルの存在など}

「全て推奨どおり」、または番号ごとに変更したい内容を返答してください（例: 「0003 は継続、0007 は破棄」）。
```

- 一括で承認できるように、「全て推奨どおり」を選べるようにする。
- 「要判断」の issue は、選択肢と推奨案を添える。
- 選択肢つきの質問ツールがあれば使ってよい。件数が多い場合は、一覧を文面で示して自由記述で返答してもらう。
- 返答が曖昧な issue には何も適用しない。

### 6. 確認後に適用する

人間が確認した内容だけを適用する。

- **破棄**: ステータスを `discarded` にし、末尾に「破棄理由」セクションを追加する。変更履歴に追記する。
- **完了扱い**: ステータスを `done` にし、根拠（マージ済みの PR・コミットなど）を変更履歴に追記する。
- **継続**: ステータスは変えず、変更履歴に「triage-issues: 継続と判断（{日付}）、{理由}」を追記する。これにより、次回の棚卸しで再び古い扱いになるのを防ぐ。
- **要更新**: 変更しない。`polish-issue` で更新することを案内する。

```markdown
## 破棄理由

{破棄日}: {理由と根拠}

## 変更履歴

- {YYYY-MM-DD} triage-issues: discarded に変更（{理由の要約}）
```

変更履歴のセクションがない issue（起票直後のものなど）は、末尾に作成する。

### 7. 報告する

次を簡潔に伝える。

- 調査した件数と、適用した結果の内訳（破棄、完了扱い、継続、要更新）
- 適用しなかった issue と理由（保留、曖昧な返答など）
- 要更新の issue への案内（`polish-issue` の実行）

## ルール

- ステータスの変更は、人間が確認した後にのみ行う。確認なしに破棄しない。
- issue ファイルを削除・移動・改名しない。
- ソースコード、テスト、設定は変更しない。変更するのは issue ファイルのステータスと履歴だけ。
- `done` と `discarded` の issue は対象外にする（ユーザーが明示した場合を除く）。
- 根拠のない推奨はしない。確認できなかった点は「推測」と明記する。
- 迷ったら破棄を避ける。
- 破棄の取り消しは、ユーザーの指示があった場合のみ、ステータスを `open` に戻して履歴に記録する。
