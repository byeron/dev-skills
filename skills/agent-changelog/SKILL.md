# agent-changelog

リポジトリ直下の `CHANGES.md` に、変更履歴を統一した形式で記載するためのルールと手順。

CHANGES.md は **agent の作業ログ** である。issue はユーザー（人間）が判断するための記録であり、CHANGES.md は agent が実際に行った変更の実績の記録である。同じ変更を両方に書くことがあるので、内容の粒度は逆に保つ。issue 側は判断の要点、CHANGES.md 側は変更の実績。

CHANGES.md では**情報を削らない**ことを重視する。記載するか迷った場合は書く。書く価値が低いと感じた場合は、削除ではなく 1 行の要約に短縮する。

## 保存場所と 1 ファイル原則

- 保存場所はリポジトリ直下の `CHANGES.md`。サブディレクトリは作らない。
- 変更履歴のファイルは 1 ファイルだけ使う。日毎・issue 毎・ブランチ毎に分けない。
- 1 ファイルであるため、項目に issue 番号を付ける規則は作らない。番号を書いてもよいが必須ではない。
- 追記のみ行う。過去の項目を書き換えない。

## CHANGES.md の形式

```markdown
# 変更履歴

このファイルには、このリポジトリに加えられた変更を agent の作業ログとして記録する。

## 未リリース

- 2026-10-25 追加: `agent-changelog` スキルを追加。形式・記載の要否・カテゴリ・バージョン自動決定を定義 #0011
- 2026-10-25 変更: `run-pairwork` の例文を実装ペアと調査ペアの 2 本に増やす
- 2026-10-24 修正: `pair-work-rule` の書き込み排他で「担当どうしは重ねない」の否定が逆になっていた語句を修正

## 0.2.0 - 2026-10-24

- 2026-10-24 追加: `pair-work-rule` と `run-pairwork` スキルを追加
- 2026-10-24 変更: リポジトリの運用ルール文書の `ペアワークのルール` 節をスキルへ移し、共通ポリシーに参照行を置く

## 0.1.0 - 2026-10-22

- 2026-10-22 追加: `issue-rule` と `create-issue` スキルを追加
```

- **unmatched セクション**（上の `## 未リリース`）を常に最上部に置く。どのバージョンにも紐づいていない変更がここに残るので、未リリースの作業と未完了の作業が一覧できる。
- 1 項目 = 1 変更 = 1 行。項目の先頭に作業した日付 `YYYY-MM-DD` を置く。
- 日付の後ろにカテゴリを 1 つ書く。カテゴリは見出しではなく行頭の語にする。時系列を保ったまま追記できるようにするため。
- 新しい項目は unmatched セクションの末尾に追記する（時系列順）。
- バージョン見出しは `## X.Y.Z - YYYY-MM-DD`。新しいバージョンを上に置く。

## 記載の要否

既定は**書く**。迷ったら書く。書かない判断はしない。

| 状況 | 書き方 |
| --- | --- |
| 読み手が知る必要のある変更（機能、挙動、設定、API、手順、不具合修正、セキュリティ） | 詳細を書く。何がどう変わったかと、影響または理由 |
| 内部のリファクタリング、テスト追加、開発ツールや CI の調整、誤字修正 | 短縮して書く。issue 番号と 1 行の要約で済ませる |
| 変更の内容が issue を読めば分かる | 短縮して書く。issue 番号と 1 行の要約で済ませる |
| 完了していない作業、途中で作った判断 | 書く。残っている作業を明記する。未完了を伏せない |
| 未リリースの項目に対する後続の修正 | 新しい行として追記する。既存の行を書き換えない |

- 短縮の基準は「CHANGES.md だけ読んでも作業の結論が分かるか」ではなく「詳細が issue で追跡できるか」である。追跡できるなら 1 行でよい。
- issue 番号を書くときは `#NNNN` の形で書く。必須ではない。番号なしで日付と内容だけ書いてもよい。
- 同じ issue に対して複数回書くことがあってよい。1 issue = 1 項目ではない。

## カテゴリ分け

既存の 6 カテゴリを使い、項目ごとに 1 つだけ選ぶ。

| 内容 | カテゴリ |
| --- | --- |
| 新しい機能・ファイル・挙動を追加した | 追加 |
| 既存の挙動・形式・手順を変えた。内部の再構成、依存の更新も含む | 変更 |
| 削除予定であることの告知 | 非推奨 |
| 機能・ファイル・設定・手順を削除した | 削除 |
| 不具合を直した | 修正 |
| 脆弱性、秘密情報の取り扱い、アクセス制御を直した | セキュリティ |

- 迷ったら「変更」を選ぶ。カテゴリの選択で作業を止めない。
- ドキュメントだけの変更、スキルの追加、運用ルール文書の構成変更も、リポジトリに加わった変更なので書く。
- 1 回の作業に複数カテゴリの変更が含まれる場合は、重い方 1 つで 1 行にする。分けた方が後の検索に有用なら 2 行に分ける。

## 文面

- 1 項目 1 行。2 文まで書いてよいが、複行にしない。
- 日付は実際に作業した日。`date +%Y-%m-%d` の実際の値を使い、推測で書かない。
- 先頭で何が変わったかを示す。文末は体言止めまたは「〜を追加」「〜を修正」「〜に増やす」の形にそろえる。「です・ます」調は使わない。
- 必要な場合のみ理由・条件・影響を添える。作業ログなので「なぜそうしたか」を書いてよい。
- 具体的な名前（ファイルパス、コマンド、オプション、設定キー、見出し名）は code 表記で書く。
- 読み手が目にする名前で書く。内部の関数名や変数名で作業内容を代用しない。
- 破壊的変更は項目の先頭に `破壊的変更:` を置き、必要な対応を書く。
- セキュリティの項目は、影響と対処を書く。悪用手順、攻撃に使える具体的な詳細、秘密情報は書かない。
- 空欄プレースホルダーを残さない。分からない内容は「未確認」と書いて、後続の行で更新する。

## バージョン番号の自動決定

- unmatched に**追加**の項目を書いたとき、agent がバージョン番号と日付を決定して、unmatched の内容を `## X.Y.Z - YYYY-MM-DD` の見出しの下へ切り出す。切り出し後は空の unmatched 見出しを最上部に残す。
- bump は、そのバージョンに含める項目の中で最も重い種別で決める。

| 含める項目の最も重い種別 | bump | 例 |
| --- | --- | --- |
| 削除、非推奨、破壊的変更 | major（`X+1.0.0`） | 0.2.0 → 1.0.0 |
| 追加 | minor（`0.Y+1.0`） | 0.1.0 → 0.2.0 |
| 修正、変更、セキュリティのみ | patch（`X.Y.Z+1`） | 0.2.0 → 0.2.1 |

- `CHANGES.md` にバージョンがまだ 1 つもない場合、最初のバージョンは `0.1.0` とする。
- **追加**を含まない変更だけの日ではバージョン見出しを作らない。項目は unmatched に残り、次の追加でまとめて切り出される。
- 切り出すとき、項目の文面を変えない。誤字と形式の統一だけ行ってよい。
- バージョン番号は agent が自動決定する。ユーザーの判断を待って開始を止める理由にしない。ユーザーが別の番号を指定した場合は、その番号を使う。

## 書く役割（書き込み排他）

- 1 作業単位について `CHANGES.md` へ書き込むのは 1 人だけである。
- ペアワークで分担した場合は、その作業単位の**記録担当**の worker が書く。もう一方の worker は CHANGES.md を読み取りのみとする。
- subagent へ委任した場合は**親 agent** が書く。子は成果物への変更だけを行い、CHANGES.md には書き込まない。親は子の報告を受けてから 1 行を追記する。
- 複数の作業単位が同時に進む場合は、CHANGES.md への追記を直列化する。1 単位の追記と形式確認を終えてから次の単位が追記する。
- unmatched の並び順を直す目的での既存行の並び替えは行わない。

## 手順

### 1. 変更の実内容を確認する

- 対象 issue があれば読んで内容を確認し、変更は実際の差分で確認する。差分が分からない状態で書かない。

```bash
git status --short
git diff
git log --oneline -5
```

### 2. カテゴリを決める

6 カテゴリから 1 つ選ぶ。迷ったら「変更」を選ぶ。

### 3. 密度を決める

「記載の要否」の表で、詳細を書くか issue 番号と 1 行の要約に短縮するかを決める。

### 4. CHANGES.md を用意する

- ファイルがなければ、上の形式の冒頭部分（`# 変更履歴` と unmatched 見出し）で作成する。
- 既存があれば、既存の項目の書式（日付の位置、カテゴリの語、文末の形）を確認してそろえる。

### 5. unmatched へ追記する

- unmatched セクションの末尾に 1 行を追記する。既存の項目は変更しない。
- 未完了の作業は残作業を明記する。

### 6. バージョンを決定する

追加の項目を書いたときは、「バージョン番号の自動決定」に従って unmatched をバージョン見出しへ切り出す。

### 7. 形式を確認する

- 日付が実際の作業日で、`YYYY-MM-DD` であるか。
- カテゴリが 6 つのうちの 1 つであり、正しい位置に追記しているか。
- 過去の項目、およびリリース済みバージョンの内容を書き換えていないか。
- 破壊的変更に対応の方法があるか。秘密情報を書いていないか。

### 8. 報告する

追記した項目のカテゴリと文面を示す。追記は作業ツリーに反映した状態で止め、コミットは行わない。コミットが必要なことも伝える。

## 例文

### 詳細を書く項目

```markdown
## 未リリース

- 2026-10-25 追加: `CHANGES.md` を agent の作業ログとして運用するため `agent-changelog` を起票。記載の要否ではなく密度で調整する方針を採用 #0011
- 2026-10-25 変更: `agent-changelog` の issue 番号規則を廃止。1 ファイルのため番号不要とし、各行を日付基準に変更 #0011
- 2026-10-25 破壊的変更: issue ファイルのメタデータテーブルから専用の追加フィールドを廃止し、ユーザー待ちの状態を `status` で表す。既存 issue のテーブルから当該フィールドを削除する対応が必要 #0008
```

### 1 行の要約に短縮した項目

```markdown
- 2026-10-24 変更: `run-pairwork` の例文 2 本で担当どうしの重なりを 1 箇所修正 #0010
- 2026-10-24 修正: `pair-work-rule` の書き込み排他 1 項目の否定の向きが逆だった語句を修正 #0009
```

### 未完了を明記した項目

```markdown
- 2026-10-25 追加: `agent-changelog` の frontmatter を作成。本文（記載の要否、カテゴリ、文面、バージョン自動決定）は未実装のまま #0011
```

## ルール

- 迷ったら書く。書かない判断をしない。短くすることはできるが消すことはしない。
- 追記するのは unmatched セクションだけ。リリース済みのバージョンの項目は書き換えない。
- 1 項目 = 1 変更 = 1 行。日付を実作業日から取る。
- カテゴリは 6 つのいずれか 1 つ。迷ったら「変更」。
- 記載の根拠は実際の差分。issue の記述だけを根拠にしない。
- `CHANGES.md` へ同じ作業単位から書き込む worker は 1 人だけ。subagent 委任時は親 agent が書く。
- バージョン番号は agent が自動決定してよい。追加を含む変更を切り出すときだけ新しいバージョン見出しを立てる。
- コミットはこのスキルでは扱わない。追記まで行って報告する。
