# agent-changelog

リポジトリ直下の `CHANGES.md` に、変更履歴を**統一した形式**で記載するスキル。
利用者・開発者・運用者が「何が変わったか」を、一貫した書き方で把握できるようにする。

> issue ファイル内の「変更履歴」セクション（その issue の磨き上げや承認の記録）とは別物。このスキルが扱うのは、リポジトリ全体の `CHANGES.md`。

## 基本方針

- **根拠は実際の差分**: issue の記述ではなく、ブランチの実際の変更（`git diff`）を基準に書く。実装が issue と異なる場合は、実装のとおりに書く。
- **読み手の視点**: 内部で何をしたかではなく、読み手にとって何が変わるかを書く。
- **追記するだけ**: リリース済みの履歴は書き換えない。編集するのは `## 未リリース` セクションだけ。
- **コミットはしない**: 追記は作業ツリーに反映し、コミットは行わない（コミットは agent-git に従って別途行う）。

## CHANGES.md の形式

```markdown
# 変更履歴

このファイルには、このリポジトリの利用者・開発者・運用者に影響する変更を記録する。

## 未リリース

### 追加
- {新しい機能や挙動} (#0003)

### 変更
- {既存の挙動の変更} (#0004)

### 非推奨
- {今後削除予定のもの} (#0005)

### 削除
- {削除したもの} (#0006)

### 修正
- {修正した不具合} (#0007)

### セキュリティ
- {修正した脆弱性} (#0008)

## [1.2.0] - 2026-10-19

### 修正
- …
```

- 構成は [Keep a Changelog](https://keepachangelog.com/) に準拠する。
- **新しいバージョンを上に**書く（最新が先頭）。
- バージョン見出しは `## [X.Y.Z] - YYYY-MM-DD`。日付は ISO 形式。
- カテゴリは、**追加 → 変更 → 非推奨 → 削除 → 修正 → セキュリティ** の順に並べる。該当する項目がないカテゴリの見出しは作らない。

## 記載ルール

### 何を記載するか

**記載する**

- 利用者や運用者から見える挙動の変更（機能、UI、出力、エラーメッセージ）
- API・CLI・設定・環境変数・ファイル形式の変更
- 互換性に影響する変更、非推奨化、削除
- セキュリティ修正
- 開発者が行う手順に影響する変更（セットアップ、ビルド、テストの実行方法など）
- 不具合の修正

**記載しない**

- 外から見える挙動が変わらない内部のリファクタリング
- テストのみの追加・修正
- CI や開発用ツールの軽微な調整
- コメントや誤字の修正
- 未リリースの変更に対する、さらなる修正（同じ項目を更新する）

迷う場合は、読み手が知っておくべきかで判断する。記載対象外と判断した場合は、その旨を報告し、CHANGES.md には書かない。

### 分類

| 内容 | カテゴリ |
|------|----------|
| 新しい機能・挙動 | 追加 |
| 既存の挙動の変更、改善 | 変更 |
| 今後削除予定の告知 | 非推奨 |
| 機能・設定・API の削除 | 削除 |
| 不具合の修正 | 修正 |
| 脆弱性の修正 | セキュリティ |

issue の種別からの目安: `bug` → 修正、`feature` → 追加または変更、`docs` → 原則記載しない、`task` → 内容による。

### 文面

- 1 つの変更につき 1 項目（1 行）にする。
- 言語は日本語。文末は体言止めまたは「〜を追加」「〜を修正」の形にそろえ、「です・ます」調は使わない。
- 先頭で何が変わったかを示し、必要な場合のみ理由や条件を補う。
- 末尾に **issue 番号を `(#NNNN)`** の形で付ける（例: `(#0003)`）。複数の issue にまたがる場合は `(#0003, #0004)`。
- 具体的な名前（コマンド、オプション、API、設定キー）は `` ` `` で囲む。
- 内部のファイル名や関数名ではなく、読み手が目にする名前で書く。

**書き方の例**

- 良い: `` `--dry-run` オプションを追加し、実行せずに変更内容を確認できるように (#0012) ``
- 良い: `ログイン時にセッションがタイムアウトした場合、エラーを表示せず再認証へ誘導するよう修正 (#0003)`
- 悪い: `auth.ts のリファクタリング` （内部の作業であり、読み手に影響がない）
- 悪い: `いろいろ修正` （何が変わったか分からない）

### 破壊的変更

利用者の対応が必要な変更は、項目の先頭に `**破壊的変更:**` を付け、移行方法を書く。

```markdown
- **破壊的変更:** 設定キー `timeout` を `request_timeout` に変更。既存の設定ファイルの書き換えが必要 (#0010)
```

### セキュリティ

- 修正済みの内容を、影響と対処の観点で書く。
- 悪用手順や、攻撃に使える具体的な詳細は書かない。
- 秘密情報（トークン、内部 URL など）は書かない。

## 手順

### 1. 変更内容を確認する

- 現在のブランチ名（`issue-NNNN-...`）から、対応する issue を特定して読む。
- ブランチの実際の差分を確認する。

```bash
base=$(git merge-base HEAD <base ブランチ>)
git diff --stat $base
git diff $base
```

### 2. 記載の要否を判断する

上記「何を記載するか」に照らして判断する。対象外なら、その理由を添えて報告し、終了する。

### 3. CHANGES.md を用意する

- `CHANGES.md` がなければ、上記の形式の冒頭部分（見出しと `## 未リリース`）で新規作成する。
- すでにあれば、既存の書き方（言語、文末、番号の形式）を確認し、そろえる。

### 4. 項目を追記する

- `## 未リリース` の、該当するカテゴリの末尾に追記する。カテゴリ見出しがなければ、規定の順序の位置に作る。
- 同じ issue の項目がすでにあれば、追記ではなく更新する。

### 5. 形式を確認する

- カテゴリの並び順が正しいか。空のカテゴリがないか。
- 文末の形がそろっているか。issue 番号が付いているか。
- 読み手の視点で書けているか。内部事情の記述がないか。
- 破壊的変更に移行方法があるか。
- 過去のバージョンの項目を変更していないか。

### 6. 報告する

追記した項目（カテゴリと文面）を簡潔に示す。コミットが必要なことも伝える。

## リリース時の処理

ユーザーからリリースの準備を依頼された場合のみ行う。

- バージョン番号は人間が決める。Claude は決めない。
- `## 未リリース` の内容を、`## [X.Y.Z] - YYYY-MM-DD` として切り出し、空の `## 未リリース` を残す。
- 内容の書き換えはしない（誤字や形式の統一を除く）。

## ルール

- 追記してよいのは `## 未リリース` のみ。リリース済みの履歴は書き換えない。
- 記載の根拠は実際の差分とする。issue の記述だけを根拠にしない。
- 1 つの変更につき 1 項目。issue 番号を必ず付ける。
- 悪用手順や秘密情報は書かない。
- コミットはしない。
