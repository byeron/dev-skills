# agent-git

このリポジトリでの git の使い方をまとめたスキル。
**git の状態を変える操作は、すべてこのスキルの規則に従って行う。**

> issue の管理方法（`issues/` の構造、ステータスの遷移、編集ルール）は `agent-issues` に従う。

## 基本方針

- **参照系は自由、変更系はこのスキル経由**: `git status` / `diff` / `log` / `show` / `branch --list` / `grep` など、状態を変えないコマンドは、どのスキルからでも使ってよい。ブランチ・インデックス・履歴・リモートを変える操作は、このスキルの規則に従う。
- **issue が起点**: ブランチもコミットも、原則として 1 つの issue に対応させる。1 issue = 1 ブランチ = 1 PR。
- **履歴を壊さない**: 破壊的な操作は行わない。必要な場合は、理由を示して人間の確認を得る。
- **安全装置を外さない**: フックや検証を迂回しない。

## 変更系の操作の前に

毎回、次を確認する。

```bash
git branch --show-current   # 現在のブランチ
git status --short          # 作業ツリーの状態
```

- 現在のブランチが想定と違う場合は、操作しない。
- 今回の作業と無関係な変更が作業ツリーにある場合は、巻き込まず、ユーザーに確認する。勝手に stash したり、破棄したりしない。

**base ブランチの特定**: AGENTS.md に指定があればそれに従う。なければ次で調べる。

```bash
git symbolic-ref --short refs/remotes/origin/HEAD   # 例: origin/main
```

## ブランチの命名規則

### 形式

```
issue-{NNNN}-{slug}
```

- issue ファイル名（`issues/NNNN-<slug>.md`）から拡張子を除き、先頭に `issue-` を付けたもの。
- 例: `issues/0003-fix-login-timeout.md` → `issue-0003-fix-login-timeout`
- issue のメタ情報表の「ブランチ」と**一致させる**。食い違っている場合は、ブランチを作らず、ユーザーに報告する。
- 一度決めた名前は変更しない。

### issue に紐づかない作業

原則として、すべての作業は issue に対応させる。issue がない場合は、create-issue での起票を提案する。ユーザーが issue なしで進めると明示した場合のみ、`misc-{slug}`（slug は英小文字・数字・ハイフン）を使う。

### ブランチの作成

実装を始めるときは、次の順に行う。

1. issue のステータスが `approved` であることを確認する（AGENTS.md のゲート）。
2. base ブランチを最新にする。
   ```bash
   git fetch origin
   git switch <base>
   git merge --ff-only origin/<base>
   ```
3. 作業ツリーがきれいなことを確認する。
4. ブランチを作成して切り替える。
   ```bash
   git switch -c issue-0003-fix-login-timeout
   ```

承認済みの issue は、base ブランチにコミット済みの状態で、そこからブランチを切る（agent-issues の「コミットの扱い」）。

## コミットの規約

### 形式

```
{type}: {概要} (#{NNNN})

{本文（任意）}
```

- `{NNNN}`: issue 番号（4 桁）。複数の issue にまたがる場合は `(#0003, #0004)`。
- 1 行目（件名）は **日本語**、全角 40 文字程度まで、末尾に句点を付けない。
- 概要は「何をしたか」を、「〜を追加」「〜を修正」のような体言止めまたは動詞の形で簡潔に書く。
- 本文は、「なぜ」変更したか、注意点、設計上の判断を書く。件名で足りる場合は省く。
- 破壊的変更は、本文に `破壊的変更: {内容と移行方法}` と書く。

### type

| type | 用途 |
|------|------|
| `feat` | 新しい機能・挙動の追加 |
| `fix` | 不具合の修正 |
| `refactor` | 挙動を変えない内部の整理 |
| `test` | テストのみの追加・修正 |
| `docs` | ドキュメント、issue ファイル、CHANGES.md の変更 |
| `chore` | ビルド、CI、依存関係、設定などの雑務 |

### issue ファイルのコミット

issue ファイルの変更は、操作に応じた次のメッセージにする。

| 操作 | メッセージ |
|------|-----------|
| 起票 | `docs: issue を起票 (#0003)` |
| 磨き上げ | `docs: issue を磨き上げ (#0003)` |
| レビューの反映 | `docs: issue にレビューを反映 (#0003)` |
| 承認 | `docs: issue を承認 (#0003)` |
| 完了 | `docs: issue を完了にする (#0003)` |
| 破棄 | `docs: issue を破棄 (#0003)` |
| 棚卸し（複数） | `docs: 古い issue を棚卸し (#0003, #0007)` |

### その他の定型メッセージ

| 場面 | メッセージ |
|------|-----------|
| CHANGES.md の更新 | `docs: 変更履歴を更新 (#0003)` |
| レビュー指摘の修正 | `fix: レビュー指摘を修正 (#0003)`（内容に応じて type を変える） |

### 粒度

- issue の「実装手順」に書かれたコミット単位に従う。
- 1 コミット = 1 つの論理的な変更。無関係な変更を混ぜない。
- 各コミットで、ビルドとテストが通る状態にする。
- WIP や一時的なコミットを残さない。

### コミットの手順

1. `git status` と `git diff` で、変更内容を確認する。
2. **ファイルを明示して** `git add` する（`git add -A` や `git add .` は使わない）。
3. `git diff --staged` で、コミットする内容を確認する。次のものが含まれていないこと。
   - 秘密情報（`.env`、鍵、トークン）
   - 今回の作業と無関係な変更
   - デバッグコード、不要な生成物
4. コミットする。
   ```bash
   git commit -m "fix: ログイン時のタイムアウトで再認証へ誘導 (#0003)" -m "{本文}"
   ```
5. `git log -1` で、メッセージが規約に沿っているか確認する。

`git config` の設定は変更しない。

### コミットしてよい場面

| 場面 | 扱い |
|------|------|
| issue の「実装手順」に書かれたコミット単位 | 実装を依頼された範囲で、そのままコミットしてよい |
| issue ファイルの変更（起票〜承認、完了） | agent-issues の「コミットの扱い」に従ってコミットしてよい |
| 他のスキルが作業ツリーに反映した変更（agent-changelog の追記、review-diff-code の修正） | 内容を示し、ユーザーの確認後にコミットする |

ユーザーが「コミットしないで」と言った場合は、コミットしない。

## push

次をすべて満たしたときだけ push する。

1. 現在のブランチが、issue のブランチである（base ブランチではない）。
2. ブランチ名が、issue のメタ情報表の「ブランチ」と一致している。
3. **review-diff-code が完了し、判定が「PR 可」である。** スキップできるのは、ユーザーが明示した場合のみ。
4. 未コミットの変更がない。
5. 追加するコミットの件名が、規約に沿っている（`git log --format=%s <base>..HEAD`）。

```bash
git push -u origin issue-0003-fix-login-timeout
```

**base ブランチへの push は原則禁止**。例外は、agent-issues の「コミットの扱い」に基づく **issue ファイルのみの変更**で、ユーザーが push を指示した場合に限る。

## Pull Request

- 1 つの issue につき PR は 1 つ。base は base ブランチ。
- **タイトル**: コミットメッセージと同じ形式（`{type}: {概要} (#{NNNN})`）。issue の「PR 情報」のタイトル案を使う。
- **本文**:

  ```markdown
  ## 概要
  {issue の「PR 情報」の要点}

  ## 関連 issue
  issues/{NNNN}-{slug}.md (#{NNNN})

  ## 受け入れ条件
  - [x] {達成した条件}
  - [ ] {未達の条件があれば、その理由}

  ## テスト
  {実行したコマンドと結果}

  ## レビュー
  review-diff-code: {N} 周、判定: {PR 可}
  ```

- PR に含める最後のコミットで、issue のステータスを `done` に更新する（`docs: issue を完了にする (#NNNN)`）。
- PR の作成方法は、環境に応じて選ぶ。`gh` が使えれば `gh pr create` を使い、使えなければ、タイトルと本文を提示してユーザーが作成する。

## マージとその後

- マージは、人間が行う（または、ユーザーが明示的に指示した場合のみ）。指示なしにマージしない。
- マージ方法（マージコミット、squash など）は、リポジトリの設定に従う。squash の場合、コミットメッセージは PR タイトルと同じ形式にする。
- マージ後のブランチ削除は、ユーザーの確認後に行う。削除は `git branch -d`（マージ済みのみ削除できる安全な形式）を使う。

## 履歴の扱い

- **push 済みのコミットの履歴は書き換えない**（rebase、amend、squash をしない）。
- base ブランチへの追従が必要な場合は、base を merge する。
  ```bash
  git fetch origin
  git merge origin/<base>
  ```
- 未 push のコミットの修正（`commit --amend`、`rebase -i` など）は、ユーザーの確認後に行う。
- タグの作成・push は、ユーザーが指示した場合のみ行う。

## 禁止と要確認の操作

**禁止**（ユーザーに指示されても、リスクを説明して再確認する）

- force push（`--force` など）。自分のブランチでの `--force-with-lease` は、下の「要確認」に従う
- `--no-verify` などによる、フックや検証の迂回。フックが失敗した場合は、原因を直す
- `git config` の変更
- 秘密情報のコミット

**要確認**（実行前に、内容と理由を示して、ユーザーの確認を得る）

- `git reset --hard`、`git clean`、`git checkout -- <path>` / `git restore`（変更の破棄）
- `git branch -D`、リモートブランチの削除
- `git rebase`、`git commit --amend`
- `git push --force-with-lease`（自分のブランチで、必要な場合のみ）
- `git stash drop`、`git stash clear`
- 作業ツリーにある、今回の作業と無関係な変更の stash

## ルール

- 状態を変える git 操作は、必ずこのスキルの規則に従う。
- 実装は、issue のステータスが `approved` のときだけ始める（ブランチを切る前に確認する）。
- コミットの件名は `{type}: {概要} (#{NNNN})`。issue 番号を必ず付ける。
- `git add` はファイルを明示する。`git add -A` / `git add .` は使わない。
- push の前に、review-diff-code を完了させる。
- base ブランチへの直接 push、force push、`--no-verify` は行わない。
- 破壊的な操作は、確認を得てから行う。
- 無関係な変更を、コミットにも stash にも巻き込まない。
