# create-issue

`issues/` に新規 issue を **1 ファイル** 起票するスキル。このスキルが定義するのは **起票までの手順**、**起票時の初期値（type / status / label）**、**起票時の例文** だけである。

> issue ファイルの保存場所、ファイル名の命名規則、書式（テンプレート）は `issue-rule` スキルに定義する。このスキルはそれを**参照する**側であり、同じ定義はここには置かない。

このスキルは「新規 issue を 1 件起票する」だけを担当し、実装・分割・具体化は扱わない。

## 起票時の初期値

- **status: `open`**（常に。`ready` 以降は後工程が扱う）
- **type: `list`**（既定）。解決方法が自明な issue のみ `task` として直接起票してよい。迷ったら `list`。`refinement` は起票時点では使わない（具体化は新しい issue を切って行う）
- **label: 検索しやすい名前**（`bug` / `implement` / `architect` / `research` など、複数可）
- 作成日は実際の日付（`date +%Y-%m-%d`）

`open` は agent が設定してよいステータスである。実装・調査・コード修正は、依頼されていない限りこのスキルでは行わない（**起票のみ**）。

## 起票までの手順

### 1. 内容を把握する

会話の文脈から次を抽出する。推測できる項目は聞き返さず埋める。埋められない項目は創作せず `未記入（要確認）` とする。**タイトル・概要が全く分からない場合のみ**ユーザーに 1 回だけ質問する。

- **タイトル**: 何についての issue か（1 行・簡潔に）
- **type**: `list` / `task`（既定 `list`。解決方法が自明なら `task`）
- **label**: `bug` / `implement` / `architect` / `research` など検索しやすい名前（複数可）
- **概要・背景**: なぜ必要か、何が問題か
- **詳細**: 再現手順、要件、仕様、候補となる解決法 など
- **受け入れ条件**: 完了と判断できる条件（`task` では必須。`list` は「列挙できた」で足りる）

### 2. `issues/` を用意する

管理場所はワーキングディレクトリ直下の `issues/`（`issue-rule`）。無ければ作成する。他の場所には作らない。

```bash
mkdir -p issues
```

### 3. ファイル名を決める

`issue-rule` の命名規則（`issues/NNNN-<slug>.md`、採番は既存最大番号 + 1、採番済み番号の再利用禁止）に従って次の番号を求め、slug を付けてファイル名を決める。既存ファイルは上書き・改名・削除しない。

### 4. テンプレートに沿って記入する

`issue-rule` のテンプレートを見出し構成ごと使い、`{...}` を実際の値で埋める。**見出し構成は変えない**（不要な節は「該当なし」）。メタデータテーブルには上の初期値を書く（`type` / `status` / `label` を埋める）。日付は `date +%Y-%m-%d` の実際の日付を使う。

### 5. 報告する

作成後、次を簡潔に伝える（ファイル全文の再掲は不要）。

- 作成したファイルのパス
- 設定した type / label（推測で決めた項目はその旨を添える）

## 例文（起票時の記入例）

`issue-rule` のテンプレートに沿った、起票直後の状態の例。

### 例文 A — type=list（既定。まずここから始める）

解決法の候補を列挙するだけの下準備 issue。`issues/0004-caching-strategy.md`

```markdown
# 0004: 検索APIのレスポンスが遅い

| 項目 | 内容 |
|------|------|
| ID | 0004 |
| type | list |
| status | open |
| label | bug, performance |
| 作成日 | 2026-10-24 |

## 概要

検索API（`GET /search`）の p95 レイテンシが 1.8s と高く、ユーザー体験を損なっている。解決法の候補を列挙し、後続 issue で具体化する。

## 背景・動機

負荷テストで検索エンドポイントのみ顕著に遅い。N+1 クエリとフルスキャンが疑わしい。原因特定前に、取りうる対策の候補を並べておきたい。

## 詳細

考えられる解決法の候補（深掘りはしない）:

- 対象テーブルにインデックス追加
- 検索結果のキャッシュ（Redis / in-memory）
- N+1 を解消する eager loading
- インデックス型ストア（Meilisearch など）への移管

## 受け入れ条件

- [ ] 候補が少なくとも 3 つ列挙されている
- [ ] 各候補に概ねのコスト/効果の目星が一言添えてある

## 関連

- 関連ファイル: src/api/search.ts
- 参考リンク: 該当なし

## メモ

どの候補を掘り下げるかは refinement の新 issue で決める。この issue は列挙のまま留める。
```

### 例文 B — type=task（解決方法が自明なときだけ直接切る）

問題と完了条件が 1 対 1 で対応する issue。`issues/0005-add-user-id-index.md`

```markdown
# 0005: users テーブルの email カラムにインデックスを追加する

| 項目 | 内容 |
|------|------|
| ID | 0005 |
| type | task |
| status | open |
| label | implement, performance |
| 作成日 | 2026-10-24 |

## 概要

`users.email` に対する lookup がフルスキャンになっている。B-Tree インデックスを追加して解消する。解決方法は自明のため直接 task として起票した。

## 背景・動機

#0004 の候補「インデックス追加」の実行単位。ログイン時の参照が件数に比例して遅くなっている。

## 詳細

- `CREATE INDEX CONCURRENTLY idx_users_email ON users (email);` 相当のマイグレーションを追加する。
- 既存の `migrations/` 命名規約に従う。

## 受け入れ条件

- [ ] マイグレーションが追加され、適用できる
- [ ] `EXPLAIN` で seq scan が index scan に変わる
- [ ] 既存テストが通る

## 関連

- 関連ファイル: migrations/
- 関連 issue: #0004

## メモ

該当なし
```

## ルール

- 1 回の呼び出しで作る issue は、ユーザーが複数依頼した場合を除き 1 件。
- **status の初期値は常に `open`**。`ready` 以降は後工程が扱うため、このスキルでは `open` 以外にしない。
- **type の既定は `list`**。`task` は解決方法が自明なときのみ。迷ったら `list`。`refinement` は起票時には使わない。
- 分割・具体化は type を書き替えず新しい issue を切る。分割元 issue には分割先への参照を残す。
- label は検索しやすい名前を付ける（`bug` / `implement` / `architect` / `research` など）。
- コード修正・調査・実装は依頼されていない限り行わない（起票のみ）。
