# issue-rule

リポジトリの `issues/` ディレクトリで issue を管理する運用の基礎ルール。issue はコードと一緒にバージョン管理される唯一の情報源であり、ユーザー（人間）と agent が同じファイルを読み書きする。

このドキュメントは**自己完結**している。issue の保存場所・ファイル名・書式（テンプレート）の定義はここだけに置く。

## 管理ディレクトリ

- 管理場所: リポジトリ直下の `issues/`。GitHub Issues などの外部サービスは使わない。
- サブディレクトリは作らない（採番と一覧性が崩れるため）。

## ファイル名の命名規則

- 形式: `issues/NNNN-<slug>.md`
  - `NNNN`: 4 桁ゼロ埋めの連番（`0001` から）。
  - `<slug>`: 内容を表す英小文字・数字・ハイフンの短い名前（50 文字程度）。日本語タイトルは内容を表す英語 slug を付ける。
  - 例: `issues/0003-fix-login-timeout.md`

### 番号の採番

- 次の番号 = `issues/` 内の既存ファイルの先頭番号の最大値 + 1（既存がなければ `0001`）。
- 番号は**再利用しない**。飛んだ番号を詰めるために既存ファイルを改名しない。
- 現在の最大番号の確認:

```bash
ls issues/ 2>/dev/null | grep -oE '^[0-9]{4}' | sort -n | tail -1
```

### 編集ルール

- ファイルは**削除・改名・移動しない**。不要になった issue は status を `discarded` にして本文に残す。
- 既存ファイルを上書きしない（追記・更新のみ）。新規 issue は常に新しい番号で切る。

## issue ファイルのテンプレート

issue は Markdown の 1 ファイル = 1 issue として書く。次の見出しとメタデータテーブルを使い、**見出し構成を変えない**（不要な節は本文に「該当なし」と書く）。`{...}` は実際の値に置き換える。

```markdown
# {NNNN}: {タイトル}

| 項目 | 内容 |
|------|------|
| ID | {NNNN} |
| type | {type} |
| status | {status} |
| label | {label1, label2} |
| 作成日 | {YYYY-MM-DD} |

## 概要

{何についての issue かを 2〜3 文で}

## 背景・動機

{なぜこの issue が必要か。現状の問題や目的}

## 詳細

{解決法の候補の列挙、または要件・仕様・設計メモ・再現手順}

## 受け入れ条件

- [ ] {完了と判断できる条件 1}
- [ ] {完了と判断できる条件 2}

## 関連

- 関連ファイル: {path/to/file}
- 関連 issue: {#NNNN}
- 参考リンク: {URL}

## メモ

{補足、未解決の疑問、分割して掘り下げるべき候補}
```

### 見出しの役割

| 見出し | 書くこと |
| --- | --- |
| `## 概要` | issue が何についてかを 2〜3 文で。ここだけ読えば内容が分かるようにする |
| `## 背景・動機` | 現状の問題、目的、きっかけ |
| `## 詳細` | 解決法の候補の列挙、要件・仕様・設計メモ、不具合なら再現手順と実際の挙動 |
| `## 受け入れ条件` | 完了と判断できる条件を箇書き（チェックボックス）で。検証可能な文にする |
| `## 関連` | 関連ファイルのパス、`#NNNN` での関連 issue 参照、参考リンク |
| `## メモ` | 補足、未解決の疑問、分割して掘り下げるべき候補。履歴の追記もここ |

### メタデータテーブルの項目

| 項目 | 値 |
| --- | --- |
| `ID` | ファイル名の `NNNN` と一致させる。本文中の参照は `#NNNN` |
| `type` | issue の種別。`list` / `refinement` / `task` のいずれか 1 つ |
| `status` | issue の状態。`open` / `ready` / `doing` / `needs-info` / `user-blocked` / `done` / `close` / `discarded` のいずれか 1 つ |
| `label` | 検索しやすい名前。複数可（カンマ区切り） |
| `作成日` | `YYYY-MM-DD`（`date +%Y-%m-%d` の実際の日付） |

issue のフィールドの追加・削除は、ユーザーの承認を得て行う。
