# run-pairwork

1 つの作業単位に worker を分担してペアワークを開始するスキル。このスキルが定義するのは **開始までの手順**、**分担時の既定（初期値）**、**分担時の例文** だけである。

> worker の定義、worker に与える 3 要素、役割分担の型、書き込み排他は `pair-work-rule` スキルに定義する。このスキルはそれを**参照する**側であり、同じ定義はここには置かない。

このスキルは「1 作業単位を 2 人の worker に分担し、相互確認まで進める」までを担当し、分担された作業自体の実施は worker の側で行う。

## 分担時の初期値

- **1 作業単位には 2 人の worker** を当てる。
- **役割の既定**は、実装系は実装役とレビュー役、調査系は立案役と批判役。
- **成果目標は worker 双方に同じ一文で共有する**。結果状態で 2 文程度に書く。
- **担当は書き込み単位で明示する**（担当するファイル / ディレクトリ / リソース）。担当どうしは重ねない。
- **記録担当を 1 人決める**。記録は対象 issue の本文に追記し、issue に新しいフィールドは作らない。
- 分担そのものでは issue の `status` を変更しない。status は作業の結果として変更する。

## 開始までの手順

### 1. 作業単位を特定する

対象 issue から、1 完結する作業単位を挙げる。その単位に成果目標と担当が書けるかを見る。成果目標を 2 文で書けない単位は分担しない。

### 2. 成果目標を共有する

同じ成果目標の一文を worker 双方に渡す。双方が同じ状態を指せていなければ、分担する前に成果目標を書き直す。

### 3. 役割と担当を決める

`pair-work-rule` の役割分担の型から、作業の性質に合う分担を選ぶ。各 worker の責任範囲と、書き込みを許可する担当ファイル・ディレクトリを書く。担当が重なる場合は、重ならないように作業単位を分割してから分担する。

### 4. 記録担当を決めて分担を issue に追記する

記録担当の worker を 1 人決める。記録担当が、対象 issue の本文に成果目標・各 worker の役割と担当範囲・記録担当を追記する。issue の既存の見出し構成と `type` / `status` / `label` は変更しない。記録担当以外の worker は issue へ書き込まない。

### 5. 実施する

各 worker が自分の担当範囲内で作業する。担当外のファイルへは書き込まない。読み取りは自由にできる。

### 6. 相互確認する

批判役・レビュー役が成果を点検し、指摘を担当 worker へ渡す。受け取った担当 worker が対応し、点検の内容と対応の結果は記録担当が同じ issue に追記する。点検の内容はこのスキルでは定義しない。

### 7. 判定して次を決める

- 成果目標を満たした → 完了扱いに進める。
- 一部しか満たさない → 不足している部分を新しい作業単位として分担し直すか、続けた worker が続ける。
- 進められない → 判断を必要とする状態として止める。新たな課題は新しい issue として起票し、既存 issue の type を書き替えない。

## 例文（分担時の記入例）

対象 issue の本文に追記した状態の例。

### 例文 A — 実装ペア（#0007）

実装役が記録担当を兼ねる。レビュー役は `migrations/` へ書き込まない。

`issues/0007-add-users-email-index.md` への追記。

```markdown
## ペアワークの分担

成果目標: users テーブルの email に一意インデックスが migration として追加され、既存データに重複がないことを確認済みになっている状態。

- 実装役（記録担当）: migrations/ 配下の新規 migration だけを書き込む。作成と適用と確認を行う
- レビュー役: 追加した migration と既存 migration の整合を読み取りで点検し、指摘を実装役へ渡す。migrations/ へは書き込まない
- 共通の制約: 既存の migration は変更しない。テスト用の fixture には触らない
```

相互確認の結果を同じ issue に追記した状態。

```markdown
## 相互確認の結果

- レビュー役の指摘: 追加した migration に CONCURRENTLY が指定されていない / ファイル名が既存の命名規約と異なる
- 実装役の対応: CONCURRENTLY を追加し、ファイル名を 0042_add_users_email_index.sql に統一した
- 残る課題: なし
```

### 例文 B — 調査ペア（#0006）

立案役が記録担当となる。批判役の指摘は立案役へ渡し、issue への追記は立案役だけが行う。

`issues/0006-search-slow-api.md` への追記。

```markdown
## ペアワークの分担

成果目標: 検索APIが遅い原因の候補が、検証可能な形（確認する箇所と期待する観測が書かれた形）で列挙済みになっている状態。

- 立案役（記録担当）: 候補を列挙し、この issue へ追記する
- 批判役: 候補の実現性と欠落を指摘し、立案役へ渡す。担当ファイルは src/api/search.ts の読み取りのみ
- 共通の制約: 本番コードへは書き込まない。候補は 1 件 1 行で観測方法と対応させる
```

相互確認の結果を同じ issue に追記した状態。

```markdown
## 相互確認の結果

- 批判役の指摘: N+1 の候補に Count query の確認が抜けている / seq scan の候補は EXPLAIN の実行がなければ検証できない
- 立案役の対応: 両候補に確認コマンドを追記した
- 残る課題: EXPLAIN の実行は実装を伴うため、task として別の issue に切る判断が必要
```

## ルール

- 成果目標の共有を省略してペアワークを開始しない。
- 担当が重なる場合は、分担する前に作業単位を分割する。
- 対象 issue への追記は記録担当 1 人だけが行う。
- 批判役・レビュー役は担当外のファイルへ書き込まない。
- 分担そのものでは issue の `status` を変更しない。
- 分担の結果として見つかった新たな課題は新しい issue として起票し、既存 issue の type を書き替えない。
- 分担ではなく subagent へ委任する単位は、subagent への委任の手順に従う。
