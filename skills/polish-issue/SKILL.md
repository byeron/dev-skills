# polish-issue

`issues/` 内の issue を「**issue だけで修正ができる**」状態まで引き上げ、人間のレビューで承認を得るスキル。
後続の実装・レビュー・PR は、承認済みの issue を唯一の情報源として行われる。

> issue の管理方法（`issues/` の構造、ステータスの遷移、編集ルール）は `agent-issues` に従う。

## ステータス

ステータスの定義・遷移・権限は agent-issues に従う。

このスキルが扱うのは、`open` / `needs-info` → `ready` → `approved` の遷移まで。`done` への更新は PR 工程で、`discarded` への変更は triage-issues が行う。

## 基本方針

- **ゴール**: 実装者（人間でも別の Claude でも）が、会話履歴を一切見ずに、この issue とリポジトリだけで実装を完了できること。ブランチ名、実装手順、検証方法まで issue に書かれていること。
- **人間の役割は判断**: 人間が全文を読まなくても判断できるよう、判断してほしい点を選択肢と推奨案つきで先頭に置く。
- **読み取り専用**: ソースコード・設定・テストは**変更しない**。変更してよいのは対象の issue ファイルのみ（調査のための読み取り、grep、既存テストや再現コマンドの実行は可）。実装は別の工程で行う。
- **事実と推測を分ける**: 確認した事実には根拠（`path:行番号`、実行したコマンドと結果）を添える。確認できていないものは「推測」と明記する。創作しない。
- **元の意図を保つ**: 起票者が書いた内容は削除・改変せず、必要なら補足・具体化する。
- **承認は人間だけ**: Claude が自分で `approved` にしない。

## 手順

### 1. 対象 issue を決める

- ユーザーが番号やパス（例: `0003`、`issues/0003-xxx.md`）を指定していればそれを使う。
- 指定がなければ `issues/` を確認し、ステータスが `open` / `needs-info` / `ready` の issue が 1 件ならそれを対象にする。複数あれば一覧を示して 1 回だけ質問する。
- ステータス別の扱い:
  - `open` / `needs-info`: ステップ 2 から通常どおり進める。
  - `ready`: すでに磨き上げ済み。ステップ 7（レビューの問いかけ）から再開する。内容の見直しを求められた場合はステップ 2 から。
  - `approved`: 承認済み。ユーザーが内容の変更を求めた場合のみ対象にし、実質的な変更を加えると `ready` に戻って再承認が必要になることを伝えてから進める。

### 2. ギャップ分析をする

issue を読み、下記「Ready の基準」に照らして不足・曖昧な箇所を洗い出す。

### 3. コードベースを調査する（読み取り専用）

不足を埋めるために必要な範囲で調査する。

- 関連ファイル・関数・設定の特定（`grep`、ファイル閲覧）
- 現状の挙動の確認（コードを追う、既存テストや再現コマンドを実行する）
- bug の場合は再現を試み、原因を特定する
- 既存の類似実装・規約・テストの書き方の確認
- 必要に応じて `git log` / `git blame` で経緯を確認
- ブランチ名・コミット・PR の規約（agent-git）を確認し、実装手順のブランチ名とコミットメッセージ案をそれに合わせる

調査は issue の解決に必要な範囲にとどめ、無関係な箇所へ広げない。

### 4. 曖昧さを解消する

- コードや証拠から決められるものは、自分で決めて理由を書く。
- 仕様判断・優先度・方針の選択など、コードからは決められないものは、issue の「判断してほしい点」に選択肢と推奨案を添えて書く（ステップ 7 で人間に問う）。
- 実装を完全にブロックする未解決事項があり、ユーザーにも確認できない場合は、「未解決の質問」に記録し、ステータスを `needs-info` にする。

### 5. issue ファイルを更新する

同じファイルを直接更新する（新規ファイルは作らない）。元の見出しは維持し、下記のセクションを追加する。

**最終的な見出しの順序**

1. メタ情報表（元から）
2. 判断してほしい点（追加）
3. 概要 / 背景・動機 / 詳細（元から）
4. 現状分析 / 原因 / スコープ / 修正方針 / 実装手順 / 影響範囲（追加）
5. 受け入れ条件（元から・書き直す）
6. テスト計画 / PR 情報 / リスク・注意点（追加）
7. 関連（元から）
8. 決定事項 / 未解決の質問 / レビュー履歴 / 変更履歴（追加）
9. メモ（元から）

**追加セクションの書き方**

```markdown
## 判断してほしい点

{なければ「なし」}

1. {論点}
   - 選択肢: A: {…} / B: {…}
   - 推奨: {A}（理由: {…}）

## 現状分析

{調査で確認した現状。根拠として path:行番号 や実行コマンドと結果を添える}

## 原因（bug の場合）

{根本原因。確認済みか推測かを明記}

## スコープ

- 対象: {この issue で行うこと}
- 対象外: {この issue では行わないこと}

## 修正方針

{方針とその理由。複数案があれば比較し、採用案と理由を書く}

## 実装手順

ブランチ: `{ブランチ名}`（メタ情報表と一致させる）

1. {変更するファイル・関数と、何をどう変えるか}
   - コミット: {コミットメッセージ案}
2. {…}
3. CHANGES.md の更新（記載対象の変更の場合。agent-changelog の規約に従う）

## 影響範囲

{変更が波及する箇所（呼び出し元、設定、ドキュメント、互換性）}

## テスト計画

- 追加・更新するテスト: {ファイルとケース}
- 実行コマンド: `{コマンド}`
- 手動確認: {必要な場合の手順と期待結果}

## PR 情報

- タイトル案: {…}
- 説明に含める要点: {…}

## リスク・注意点

{落とし穴、後方互換性、パフォーマンス、セキュリティなど}

## 決定事項

{人間が判断した内容と日付。なければ「なし」}

## 未解決の質問

{なければ「なし」}

## レビュー履歴

{人間のレビューの記録（ステップ 7）。なければ「なし」}

## 変更履歴

- {YYYY-MM-DD} polish-issue: {何を追加・変更したかの要約}
```

あわせて以下を更新する。

- 「受け入れ条件」: 客観的に検証できる形に書き直す（Ready の基準 5 を参照）
- 「関連」: 実際に確認したファイルパスを具体的に列挙する
- メタ情報表: 優先度を見直し、ブランチ名が埋まっていることを確認する

### 6. 単独で読めるか最終確認する

文脈を持たない実装者になったつもりで issue を頭から読み直し、Ready の基準をすべて満たすか確認する。満たさない項目があれば、ステップ 3 または 4 に戻る。

### 7. 人間にレビューを依頼する

基準を満たしたら、ステータスを `ready` にし、人間に次の形式で問いかける。選択肢つきの質問ツールがあれば「承認」と「問題点あり（自由記述）」の 2 択で使い、なければ文面で聞く。

```
issues/0003-fix-login-timeout.md を磨き上げました。レビューをお願いします。

【判断してほしい点】
1. {論点}: A / B（推奨: A。理由: …）

【概要】
- スコープ: …（対象外: …）
- 修正方針: …
- 受け入れ条件: …

「承認」、または問題点を自由に記述してください。
```

判断してほしい点がなければ、その欄は省く。

**返答ごとの動き**

| 返答 | 動き |
|---|---|
| 「承認」 | ステータスを `approved`、承認日を記入し、レビュー履歴と変更履歴に記録する。実装に進めることを伝えて終了 |
| 問題点の記述 | 指摘をレビュー履歴に記録し、issue を修正（必要なら再調査）して `ready` に保ち、ステップ 6 → 7 を繰り返す |
| 判断点への回答 | 「決定事項」に記録し、「判断してほしい点」から外して issue に反映する。残りがあればステップ 7 を繰り返す |

**承認の厳格化**

- 人間が明確に「承認」と答えた場合のみ `approved` にする。
- 「たぶん大丈夫」「〜を直したら承認」のような曖昧・条件付きの返答は、承認ではなく指摘として扱う。
- 承認前に判断してほしい点が残っている場合は、先にその回答を求める。

### 8. 報告する

次を簡潔に伝える。

- 対象 issue のパスと新しいステータス
- 調査で分かった要点（原因、修正方針の骨子）
- 人間に判断・確認してほしい点（あれば）

## Ready の基準

以下をすべて満たしたときだけ `ready` にする。

1. **問題が明確**: 何が問題か、あるいは何を実現したいかが、他の資料なしで理解できる。
2. **現状が検証済み**: bug は再現または原因箇所を特定済み。feature / task は現状の実装を確認済み。根拠が書かれている。
3. **スコープが明確**: 「やること」と「やらないこと」が分かれている。
4. **修正方針と実装手順が具体的**: ブランチ名、変更するファイル・関数と変更内容、コミットの区切りが書かれ、迷わず着手できる。
5. **受け入れ条件が検証可能**: 「正しく動く」のような曖昧な表現ではなく、入力・操作と期待結果、またはテストの成否で判定できる。
6. **テスト計画がある**: 実行できるコマンドと確認観点が書かれている。
7. **PR 情報がある**: タイトル案と、説明に含める要点が書かれている。
8. **自己完結している**: 「前述の」「あの件」「さっきの」など会話に依存した表現や、未定義の略語がない。他の issue への依存は番号を明記する。
9. **ブロックする未解決事項がない**: 残っている疑問が実装を妨げない。人間の判断が必要な点は「判断してほしい点」に選択肢と推奨案つきで整理されている。

## ルール

- 変更してよいのは対象の issue ファイルのみ。ソースコード・テスト・設定には触れない。
- `approved` にするのは、人間が明確に承認したときだけ。Claude が自分で承認しない。
- 承認後に issue の内容（スコープ、方針、実装手順、受け入れ条件など）を実質的に変更したら、ステータスを `ready` に戻し、承認日を `未承認` にして、再承認を求める。誤字の修正など意味が変わらない変更は除く。
- 事実には根拠を、推測には「推測」の明記を付ける。
- 元の見出し構成は維持し、セクションは追加する形にする。
- 1 回の呼び出しで磨く issue は 1 件。
- 調査の結果、issue が重複・不要・分割すべきと分かった場合は、勝手に統合・削除せず、その旨を報告してユーザーに判断を仰ぐ。
