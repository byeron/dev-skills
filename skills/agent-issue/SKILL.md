# agent-issues

GitHub Issues などは使わず、**リポジトリの `issues/` ディレクトリで issue を管理する**運用のルール。
issue はコードと一緒にバージョン管理され、Claude と人間が同じファイルを読み書きする。

issue は開発の**唯一の情報源**であり、人間の主な仕事は、その issue に対する判断（レビューと承認）である。

## ディレクトリとファイル

- 管理ディレクトリ: リポジトリ直下の `issues/`
- ファイル名: `issues/NNNN-<slug>.md`
  - `NNNN`: 4 桁ゼロ埋めの連番（`0001` から）
  - `<slug>`: 内容を表す英小文字・数字・ハイフンの短い名前（50 文字程度まで）
  - 例: `issues/0003-fix-login-timeout.md`
- 番号は**再利用しない**。次の番号は、既存ファイルの最大番号 + 1。
  ```bash
  ls issues/ 2>/dev/null | grep -oE '^[0-9]{4}' | sort -n | tail -1
  ```
- ファイルは削除・改名・移動しない（不要になった issue は、ステータスを `discarded` にして残す）。
- サブディレクトリは作らない。番号の採番が崩れるため。

## ファイルの構造

### メタ情報表

ファイル先頭の見出しの下に置く表。値は 1 行ずつ。

| 項目 | 内容 | 値 |
|------|------|----|
| ID | 4 桁の連番 | `0003` |
| 種別 | issue の種類 | `bug` / `feature` / `task` / `docs` / `question` |
| ステータス | 現在の状態 | 下記「ステータスと遷移」 |
| 優先度 | 対応の優先度 | `high` / `medium` / `low`（不明なら `medium`） |
| 作成日 | 起票日 | `YYYY-MM-DD` |
| ブランチ | 実装用のブランチ名 | `issue-0003-fix-login-timeout` |
| 承認日 | 人間が承認した日 | `YYYY-MM-DD`、未承認は `未承認` |
| ラベル | 自由なラベル | `auth, backend` |

### セクション

セクションは、工程が進むにつれて増える。見出しの構成は、後続の工程でも維持する。

| 段階 | セクション | 担当スキル |
|------|-----------|-----------|
| 起票 | 概要、背景・動機、詳細（期待する挙動）、受け入れ条件、関連、メモ | create-issue |
| 磨き上げ | 判断してほしい点、現状分析、原因、スコープ、修正方針、実装手順、影響範囲、テスト計画、PR 情報、リスク・注意点 | polish-issue |
| レビュー | 決定事項、未解決の質問、レビュー履歴、変更履歴 | polish-issue |
| 棚卸し | 破棄理由 | triage-issues |

各テンプレートの詳細は、それぞれのスキルを参照する。

## ステータスと遷移

| ステータス | 意味 |
|------------|------|
| `open` | 起票直後。磨き上げ前 |
| `needs-info` | ブロックする未解決事項があり、ユーザーの判断待ち |
| `ready` | 磨き上げ完了。人間のレビュー待ち |
| `approved` | 人間が承認済み。実装に着手してよい |
| `done` | 実装・マージ済み |
| `discarded` | 不要になったため破棄。ファイルは残す |

```
open ──polish-issue──▶ ready ──人間の承認──▶ approved ──マージ──▶ done
  │                      ▲                       │
  └──▶ needs-info ───────┘                       └─ 内容を実質的に変更 ─▶ ready に戻る

open / needs-info / ready / approved ──triage-issues（人間の確認後）──▶ discarded
```

**誰が、いつ変えてよいか**

| 遷移 | 変更する人・スキル | 条件 |
|------|--------------------|------|
| （新規）→ `open` | create-issue | 起票時 |
| `open` → `ready` | polish-issue | Ready の基準をすべて満たしたとき |
| `open` → `needs-info` | polish-issue | ブロックする未解決事項があるとき |
| `ready` → `approved` | **人間のみ**（polish-issue が記録） | 人間が明確に「承認」と答えたとき |
| `approved` → `ready` | polish-issue | 承認後に、スコープ・方針・実装手順・受け入れ条件などを実質的に変更したとき。承認日は `未承認` に戻す |
| `approved` → `done` | 実装工程（PR の最後のコミット） | 受け入れ条件を満たし、PR を出すとき |
| 各ステータス → `discarded` / `done` | triage-issues | 人間が確認した後のみ |
| `discarded` → `open` | ユーザーの指示があるとき | 理由を履歴に記録する |

**Claude が自分で `approved` にすることは禁止。**

## ブランチ・コミット・PR・CHANGES.md との対応

ブランチ名・コミットメッセージ・PR の規約は、agent-git に従う（このスキルでは定義しない）。実装ブランチ名は、メタ情報表の「ブランチ」に記載されたものを使う。

CHANGES.md への記載は、agent-changelog の規約に従う（項目の末尾に `(#NNNN)` を付ける）。

issue 番号は、`#NNNN`（4 桁）で参照する。他の issue への依存や関連は、この形式で書く。

## issue の探し方と読み方

**対象の issue を特定する**

```bash
git branch --show-current                  # issue-0003-fix-login-timeout
ls issues/0003-*.md                         # 対応する issue ファイル
```

**一覧と検索**

```bash
grep -H -m1 '^| ステータス |' issues/*.md   # 各 issue のステータス
grep -H -m1 '^# ' issues/*.md               # 各 issue のタイトル
grep -rli '<キーワード>' issues/            # キーワードで検索
```

**読む順序**（実装や確認のとき）

1. メタ情報表（ステータスが `approved` か、ブランチ名は何か）
2. 判断してほしい点、決定事項（人間の判断が反映されているか）
3. スコープ（対象と対象外）
4. 実装手順、テスト計画
5. 受け入れ条件
6. 関連、リスク・注意点

## 使い方の原則

- **issue を唯一の情報源にする**: 実装は issue の「実装手順」に従い、「スコープ」の対象外には手を付けない。会話で決まったことは、必ず issue に書き戻す。
- **実装のゲートと、実装中に issue の誤りを見つけたときの扱いは、AGENTS.md の「ルール」に従う。**
- **issue を増やすのは人間の判断を経て**: review-code などで見つけた課題は、人間が選んだものだけ起票する。

## 編集ルール

- 起票者が書いた内容は、削除・改変しない。必要なら補足・具体化する。
- 「変更履歴」と「レビュー履歴」は追記のみ。過去の行は書き換えない。
- 日付は `YYYY-MM-DD`。日付は実際の日付（`date +%Y-%m-%d`）を使い、推測で書かない。
- 事実には根拠（`path:行番号`、コマンドと結果）を添え、推測には「推測」と明記する。
- 1 回の作業で更新する issue は、原則 1 件。
- ステータスの変更は、メタ情報表と、変更履歴の記録を同時に行う。

## コミットの扱い

issue ファイルの変更は、他の変更と同じくコミット対象とする（コミットの操作とメッセージは agent-git に従う）。既定の運用は次のとおり（プロジェクトに合わせて調整する）。

- 起票から承認まで（`open` → `approved`）の変更は、base ブランチ上で行い、コミットしてから実装ブランチを切る。
- 実装ブランチでは、issue のステータス更新（`done`）を PR の最後のコミットに含める。
- 実装中に issue を更新する場合（逸脱の修正）は、実装ブランチ上で行い、`ready` に戻したうえで人間の判断を仰ぐ。

## 工程とスキルの対応

| 工程 | スキル |
|------|--------|
| 起票 | create-issue |
| 磨き上げ・人間のレビュー・承認 | polish-issue |
| 実装 | （`approved` の issue を対象に）issue の実装手順に従う |
| 変更履歴の記載 | agent-changelog |
| 差分のレビュー（push・PR の前） | review-diff-code |
| メインブランチのコードのレビュー（課題の洗い出し） | review-code |
| 古い issue の棚卸し | triage-issues |

## 不整合を見つけたとき

AGENTS.md、このスキル、他のスキルの記述が食い違っている場合は、黙ってどちらかに合わせず、食い違いの箇所をユーザーに報告して確認する。
