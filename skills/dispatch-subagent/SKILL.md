# dispatch-subagent

1 つの作業単位を subagent に委任するスキル。このスキルが定義するのは **委任までの手順**、**委任時の既定（初期値）**、**委任時の例文** だけである。

> subagent へ分割してよいかの条件、`comm-agent/` の保存場所とファイル名の命名規則、依頼・報告のフォーマット（テンプレート）は `subagent-rule` スキルに定義する。このスキルはそれを**参照する**側であり、同じ定義はここには置かない。

このスキルは「1 作業単位を 1 subagent に委任し、報告を受け取る」までを担当し、委任した作業自体の実装・調査は subagent の側で行う。

## 委任時の初期値

- **1 回の委任 = 1 作業単位 = 1 subagent**。複数の作業単位を 1 つの依頼にまとめない。
- **成果目標は結果状態で 2 文程度**。手順の列挙にはしない。
- **責任範囲は書き込み単位で明示する**（許可するファイル / ディレクトリ / リソースを 1 つの単位に絞る）。
- **完了条件は subagent 自身が検証可能な形**で 2 つ以上書く（実行コマンドや確認項目）。
- **成果物と報告の送り先は `comm-agent/` の依頼ファイル**。
- 委任そのものでは issue の `status` を変更しない。status は作業の結果として変更する。

## 委任までの手順

### 1. 作業単位を切り出す

対象 issue の内容から、独立して完結する作業単位を書く。各単位に成果目標・責任範囲・入力・完了条件を書けるかを見る。書けない単位は委任対象ではない。

### 2. 分割してよいか判定する

`subagent-rule` の分割の条件（入力と完了条件が明示されている / 書き込み対象が重複しない）に照らす。どちらか 1 つでも満たさなければ委任しない。単一の agent で続けるか、入力を確定させてから 1 へ戻る。

### 3. 依頼ファイルを用意する

`subagent-rule` の命名規則（`comm-agent/NNNN-<unit-slug>.md`）でファイル名を決め、`comm-agent/` に作成する。ディレクトリが無ければ作る。委任ファイルのテンプレートに見出し構成ごと依頼を記入する。

```bash
mkdir -p comm-agent
```

### 4. subagent を起動して依頼を渡す

依頼本文（成果目標 / 責任範囲 / 入力 / 完了条件 / 成果物 / 報告指示）をそのまま subagent に渡す。起動後の口頭の追加指示で責任範囲を広げない。

### 5. 報告を受け取る

subagent からの報告は `subagent-rule` の報告フォーマット（状態 / 成果 / 成果物 / 完了条件判定 / 新規依存・阻害要因 / 次の行動）で受け取り、依頼したファイルと同じ `comm-agent/` ファイルの報告見出しに追記する。報告が無い作業単位は未完了として扱う。

### 6. 判定して次を決める

- `完了` → 成果物と `完了条件判定` を確認し、issue の作業を進める。
- `一部完了` → 未充足の完了条件を新しい作業単位として切り出すか、親が続ける。
- `ブロック` → 親が判断する。追加入力が必要なら入力を集め、新たな課題は新しい issue として起票する。既存 issue の type は書き替えない。

## 例文（委任時の記入例）

`subagent-rule` の委任ファイルのテンプレートに沿った、委任直後と報告受領後の状態の例。

### 例文 A — 複数ファイルの調査（2 作業単位に分割）

issue `#0006` の調査を、測定とレビューの 2 作業単位に分割する。書き込み先が重ならないように切る。

`comm-agent/0006-search-measure.md`

```markdown
# 0006: 検索APIのレイテンシ要因を測定して特定する

対象 issue: #0006

## 依頼（親 -> 子 subagent）

成果目標: 検索APIのレイテンシがどの箇所で発生しているかを、計測結果として特定済みになっている状態。p95 が高い箇所が 1 つ以上、数値付きで示されている。
責任範囲: bench/search-latency.md 新規ファイルのみ（範囲外への書き込みは禁止）
入力: src/api/search.ts、src/db/users.ts、issues/0006-search-slow-api.md、既存の bench/ ディレクトリの構成
完了条件: 実行した計測コマンドと得られた数値が bench/search-latency.md に並んでいる / 各数値が対象コードのどの箇所に対応するかが書かれている
成果物: bench/search-latency.md
報告指示: 実行中に新たな依存・競合・範囲外の問題を見つけた場合は、その作業を中断して親に報告する

## 報告（子 subagent -> 親）

未実行
```

報告を受領後に同じファイルへ追記した状態。

```markdown
## 報告（子 subagent -> 親）

状態: 完了
成果: p95 1.8s のうち 1.2s が users テーブルの seq scan、0.4s が N+1 クエリと切り分けた。
成果物: bench/search-latency.md
完了条件判定: 計測コマンドと数値の列挙は充足 / 数値とコード箇所の対応付けは充足
新規依存・阻害要因: 計測に test/fixtures の追加が必要だった。本番コードには手を入れていない。
次の行動: seq scan の解消と N+1 の解消を別 issue に切り出してよい判断をする
```

同じ issue のもう 1 単位は `comm-agent/0006-search-review.md`（責任範囲は docs/search-notes.md 新規のみ）とし、`bench/search-latency.md` へは書き込まない。

### 例文 B — 実装とレビュー（責任範囲が交差しない 2 単位）

実装 unit を `comm-agent/0007-add-email-index.md`（責任範囲は migrations/ 配下の新規ファイル）、レビュー unit を `comm-agent/0007-review-migration.md`（責任範囲は comm-agent/0007-review-migration.md への追記のみ、実装ファイルは読み取りのみ）として切る。

報告が `ブロック` になった例。

```markdown
## 報告（子 subagent -> 親）

状態: ブロック
成果: 追加した migration の構文確認まで完了。適用は実施していない。
成果物: comm-agent/0007-review-migration.md
完了条件判定: 既存 migration への命名規約準拠は充足 / CONCURRENTLY 指定の確認は未充足（migration/0042_add_users_email_index.sql が見つからず対象を特定できない）
新規依存・阻害要因: migrations/ の実ファイル名が命名規約と異なる可能性があり、対象の特定に親の判断が必要。書き込み範囲外のため触っていない。
次の行動: migrations/ の命名規約を確定してからレビュー unit を再委任する。規約自体が課題なら新 issue にする
```

## ルール

- 1 回の委任で作る依頼は 1 作業単位。複数の作業単位を 1 依頼にまとめない。
- 責任範囲に書いていないファイル・ディレクトリへの書き込みを指示しない。
- 同一ファイルへ複数の subagent を書き込ませない（同じ issue でも責任範囲を分ける）。
- 依頼には手順ではなく成果目標を書く。完了条件の判定は subagent 自身にさせる。
- 委任の成否は subagent の報告で判定し、成果物の有無だけで完了とみなさない。
- 委任そのものでは issue の `status` を変更しない。
- 委任中に見つかった新たな課題は新しい issue として起票し、既存 issue の type を書き替えない。
