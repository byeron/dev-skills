# review-diff-code

現在のブランチの差分を 7 の観点でレビューし、修正可能な指摘を修正して、PR 作成や push に進んでよい状態かを判定するスキル。

発動するタイミングと、レビュー後に続く工程の順序はリポジトリの運用ルール文書が持つ。このスキルが定義するのは、観点、周回の手順、issue の受け入れ条件・スコープとの照合、指摘の記録形式と重大度、判定と報告の形式である。

## 担当範囲

| 担当 | 内容 |
| --- | --- |
| 担当する | 差分の特定、7 観点のレビュー、修正可能な指摘の修正、判定と報告 |
| 担当しない | commit、push、PR の作成、作業記録への記載 |

- commit・push・PR の作成はこのスキルでは行わない。コミットが必要であると分かった場合はその旨を報告するまでであり、コミットの可否をユーザーに尋ねない。コミットの手順と可否は `git-rule` が持ち、agent は `git-rule` に従ってコミットする。コミットが適切かどうかの判断はユーザーが持つ。
- レビューの後には作業記録への記載と commit / PR / push が続く。このスキルは先頭のレビューと、レビューで生じた指摘の修正までを行う。
- **issue のステータスは扱わない**。判定は差分の状態についてだけ行う。issue の承認と完了の状態の判断は運用側が持つ。

## 基本方針

- **issue が基準**: レビューの基準は、ブランチに対応する issue の受け入れ条件・スコープ・実装手順と、リポジトリの運用ルール文書に書かれた規約である。
- **周回で見落としを減らす**: 1 周で終わらせない。修正が新たな問題を生むことがあり、先入観で見落とすこともあるため、周ごとに見方を変えて確認する。
- **人間の仕事は判断**: 明確な欠陥は自分で直す。仕様の判断やトレードオフが絡むものは直さず、選択肢と推奨案を添えてユーザーに渡す。
- **根拠のない「問題なし」は禁止**: 観点ごとに「何を確認して問題なしと判断したか」を書く。
- **判定する前に修正を終える**: 判定結果を出す前に、自分で修正できる指摘はすべて修正し終えている。

## 7 つの観点

| # | 観点 | 主な確認事項 |
| --- | --- | --- |
| 1 | 要件適合性 | 受け入れ条件をすべて満たすか。issue のスコープ外の変更が混ざっていないか。issue の実装手順と食い違っていないか |
| 2 | 正しさ・ロジック | バグ、境界値、null・空、エラー処理、例外経路、競合・並行性、型や単位の誤り |
| 3 | テスト | 網羅性と質。受け入れ条件に対応するテストがあるか。異常系と境界値。テストが実装を追認するだけになっていないか |
| 4 | セキュリティ | 入力検証、認証・認可、インジェクション、秘密情報の混入、ログへの機密出力、依存パッケージの追加 |
| 5 | 設計・保守性 | 責務の分担、命名、重複、複雑度、既存の設計・規約との一貫性、不要な抽象化や過剰設計 |
| 6 | 性能・信頼性・互換性 | 計算量、N+1、リソースリーク、リトライとタイムアウト、後方互換性、マイグレーション、影響範囲 |
| 7 | ドキュメント・差分の衛生 | 変更に合わせてコメントとドキュメントが更新されているか。デバッグコード、コメントアウトされたコード、不要ファイル、生成物の混入。コミット分割の粒度とメッセージ |

- 観点を増やす場合はこの表に行を追加する。周回の手順は観点数に依存しない。
- 1 周のなかで 7 観点を同時には見ない。観点ごとに見る。

## 手順

### 1. 前提を確認する

- 現在のブランチを特定する（`git branch --show-current`）。
- base ブランチを特定する。リポジトリの運用ルール文書に指定があれば従う（このリポジトリでは AGENTS.md の `git のルール` が base ブランチ名を定めている）。指定がない場合は remote の既定ブランチ（`git remote show origin` の `HEAD branch`）を調べる。取得できないときは `main` / `master` のどちらかが存在するか確認して決める。それでも決まらないときだけユーザーに 1 回尋ねる。
- 対応する issue を特定して読む。`issues/` のファイル名と差分の内容から探し、受け入れ条件・スコープ・実装手順を確認する。変更そのものは実際の差分で確認し、issue の記述だけを根拠にしない。
- 対応 issue が見つからない場合はユーザーに 1 回だけ確認する。issue なしで続行する場合は観点 1 を「issue なし」として扱い、観点 2 以降でレビューする。
- 作業ツリーの状態を確認する（`git status --short`）。未コミットの変更と未追跡ファイルもレビュー対象に含める。

### 2. 差分を取得する

```bash
base_ref=origin/main                                  # 手順 1 で決めた base ブランチ
base=$(git merge-base "$base_ref" HEAD)
git diff --stat "$base"            # 変更ファイルの一覧（未コミットの変更を含む）
git diff "$base"                   # 差分本体（未コミットの変更を含む）
git log --oneline "$base"..HEAD    # コミット一覧
git status --short                 # 未追跡ファイルの確認
```

- `git merge-base` は 2 つのリビジョンを要求する。base のリファレンスを必ず与える。
- 変更ファイルは差分だけでなく**ファイル全体**を読む。変更箇所の呼び出し元・呼び出し先・関連するテストも確認する。
- 未追跡ファイルは `git diff` の出力に出ない。`git status --short` で拾って、内容を直接読む。
- 差分が大きい場合はファイル単位に分けて確認する。分けた場合も 1 周ごとに全観点を通す。

### 3. 周回レビューをする

**周ごとの狙い**

| 周 | 狙い |
| --- | --- |
| 1 周目 | 7 観点すべてで差分全体を確認する。リポジトリにテスト・lint・型チェックの仕組みがあれば実行する |
| 2 周目 | 1 周目の指摘の修正を検証し、修正後の差分全体を 7 観点で再確認する。修正が新たな問題を生んでいないか見る |
| 3 周目 | 先入観を外した通しレビュー。これまでの指摘ログを見ずに、変更ファイルを逆順に読み、初見のレビュアーとして 7 観点で確認する。その後でログと突き合わせる |
| 4 周目以降 | 直前の周で新規の指摘があった場合のみ。直前の修正の検証と再確認 |

**各周のやり方**

1. 観点ごとに差分を読み直す。
2. 観点ごとに、指摘と「確認したこと」を記録する。指摘がない場合も、確認した内容を書く。
3. 指摘を手順 4 の方針で処理する。
4. 修正後は、関連するテストと lint などを再実行する。

**終了条件**

- **最低 3 周は必ず行う**。1 周目・2 周目で指摘が 0 件でも 3 周目は省略しない。
- 3 周目以降は、直前の周で修正が必要な新規指摘が 0 件であり、過去の修正がすべて検証済みなら終了する。
- 5 周に達しても新規指摘が出続ける場合は打ち切り、残りの指摘を報告する。

### 4. 指摘を処理する

**記録形式**

```
[R{周}-{連番}] {観点} / {重大度}
場所: {path}:{行番号}
問題: {何が問題か}
根拠: {なぜ問題と言えるか。再現手順、該当コード、issue の該当箇所}
対応: {修正した内容 / 修正案 / 判断依頼}
```

**重大度**

| 重大度 | 基準 |
| --- | --- |
| blocker | 動作しない、データ損失、重大なセキュリティ問題、受け入れ条件の未達 |
| major | バグ、重要な経路のテスト不足、後方互換性の破壊 |
| minor | 保守性、軽微な不整合、小さなテスト不足 |
| nit | 好みの範囲、表記の揺れ |

**処理の方針**

- blocker と major は必ず対応する。
- 自分で修正してよいのは、issue のスコープ内で正解が明確なものだけ。修正は作業ツリーに反映し、コミットは行わない。
- 修正せずにユーザーへ渡すのは、仕様の解釈が分かれるもの、トレードオフがあるもの、スコープの拡大を伴うもの。選択肢と推奨案を添える。
- minor は範囲内で自明なものは修正する。nit は報告のみ。
- issue 自体の誤りや不足が見つかった場合は、コードで回避しない。issue の修正が必要である旨を報告し、ユーザーの判断を求める。
- 差分の範囲外にある既存の問題は修正せず、「範囲外の気づき」として別に報告する。
- テストを通すためにテストを弱めたり削除したりしない。

**指摘の記入例**

```
[R2-1] 正しさ・ロジック / major
場所: scripts/build.sh:104
問題: 差分取得のコマンドが base のリファレンスを与えておらず、`git merge-base` が失敗する
根拠: `git merge-base` は 2 つのリビジョンを要求する。1 つしか与えないと usage エラーになる
対応: 修正済み。base のリファレンスを変数に受け取る形に書き換えた

[R3-2] 要件適合性 / major
場所: src/parser/normalize.py:42
問題: issue #0007 の受け入れ条件 3「空入力で例外を出さない」を満たしていない
根拠: 空文字を渡すと `IndexError` が出る。再現手順: `normalize("")`
対応: 判断依頼。空入力を無視して `None` を返す案と、空入力も有効な値として `""` を返す案がある。推奨は後者。呼び出し側が空入力を正常系として扱えるため
```

### 5. 最終報告をする

```markdown
## レビュー結果: {PR 可 / 要判断 / 要修正}

- 対象: {現在のブランチ} → {base ブランチ}（issue: {#NNNN または「なし」}）
- 実施: {N} 周（5 周で打ち切った場合はその旨を書く）
- 実行したチェック: {コマンドと結果。仕組みがなければ「なし」}

### 指摘の集計

| 観点 | blocker | major | minor | nit | 内訳 |
| --- | --- | --- | --- | --- | --- |
| 1 要件適合性 | 0 | 1 | 2 | 0 | 修正済み 2 / 判断待ち 1 |
| 2 正しさ・ロジック | 0 | 0 | 1 | 2 | 修正済み 1 / 報告のみ 2 |

（行は 7 観点ぶん並べ、0 の観点も省略しない。内訳には「修正済み」「残り」「判断待ち」を書く）

### 判断をお願いしたい点

1. {論点}: {選択肢 A} / {選択肢 B}（推奨: {A}。理由: {理由}）

### 残っている指摘

{未対応の指摘と、未対応である理由。なければ「なし」}

### 範囲外の気づき

{差分の範囲外で見つけた既存の問題。なければ「なし」}

### 修正した内容

{主な修正の要約}
```

**判定の基準**

- 未修正の blocker または major がある → **要修正**
- 判断待ちがある → **要判断**
- blocker と major が残っておらず、判断待ちもない → **PR 可**

**報告の注意**

- 判定語は差分の状態を表すラベルであり、このスキルが PR や push を行う意味ではない。PR を出さない運用では、**PR 可** は push に進んでよいという意味になる。
- 修正を行った場合は、修正した内容とコミットが必要である旨を報告する。コミットそのものは行わず、可否をユーザーに尋ねず、`git-rule` に従ってコミットが進む。
- 5 周で打ち切った場合は、その旨と残っている指摘を明記する。

## ルール

- 最低 3 周、最大 5 周。1 周で完了としない。
- 7 の観点すべてを毎周確認する。
- commit、push、PR の作成は行わない。
- 指摘に根拠を付ける。根拠がない推測は「推測」と明記する。
- 過去の周の結果を「確認済み」として信用しない。修正後の状態を再確認する。
- issue のスコープ外の変更を行わない。範囲外の既存問題は報告だけ行う。
- テストを通すためにテストを弱めたり削除したりしない。
- 判定は差分の状態についてだけ行う。issue のステータスは扱わない。
