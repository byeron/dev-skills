# review-diff-code

ブランチの差分をレビューするスキル。**PR を出す前、または push する前に必ず実行する。**
徹底的なレビューを最低 3 周、最大 5 周行い、7 つの観点で確認する。

> issue の管理方法（`issues/` の構造、ステータスの遷移、編集ルール）は `agent-issues` に従う。

## 基本方針

- **issue が基準**: レビューの基準は、ブランチに対応する承認済みの issue（受け入れ条件・スコープ・実装手順）と、リポジトリの規約。
- **周回で見落としを減らす**: 1 周で終わらせない。修正が新たな問題を生むことがあり、先入観で見落とすこともあるため、周ごとに見方を変えて確認する。
- **人間の仕事は判断**: 明確な欠陥は自分で直す。仕様判断やトレードオフが絡むものは直さず、選択肢と推奨案をつけて人間に渡す。
- **根拠のない「問題なし」は禁止**: 観点ごとに「何を確認して問題なしと判断したか」を書く。
- **push も PR 作成もしない**: このスキルはその手前までを担当する。

## 7 つの観点

| # | 観点 | 主な確認事項 |
|---|------|--------------|
| 1 | 要件適合性 | 受け入れ条件をすべて満たすか。issue のスコープ外の変更が混ざっていないか。実装手順と食い違っていないか |
| 2 | 正しさ・ロジック | バグ、境界値、null・空、エラー処理、例外経路、競合・並行性、型や単位の誤り |
| 3 | テスト | テストの網羅性と質。受け入れ条件に対応するテストがあるか。異常系・境界値。テストが実装を追認するだけになっていないか。テスト計画のコマンドが通るか |
| 4 | セキュリティ | 入力検証、認証・認可、インジェクション、秘密情報の混入、ログへの機密出力、依存パッケージの追加 |
| 5 | 設計・保守性 | 責務の分離、命名、重複、複雑度、既存の設計・規約との一貫性、不要な抽象化や過剰設計 |
| 6 | 性能・信頼性・互換性 | 計算量、N+1、リソースリーク、リトライやタイムアウト、後方互換性、マイグレーション、影響範囲 |
| 7 | ドキュメント・差分の衛生 | コメントやドキュメントの更新、CHANGES.md の記載（記載対象の変更に記載があるか、agent-changelog の規約に沿っているか）、デバッグコードや不要ファイルの残存、生成物の混入、コミット粒度とメッセージの規約 |

観点を増やす場合は、この表に行を追加する（周回の手順は観点数に依存しない）。

## 手順

### 1. 前提を確認する

- 現在のブランチ名と base ブランチ（AGENTS.md の規約、なければ `main` / `master`）を特定する。
- ブランチ名（`issue-NNNN-...`）から対応する issue を探して読む。見つからなければユーザーに 1 回だけ確認する。
- issue のステータスを確認する。`approved` でなければ、その旨を伝えて続行してよいか確認する。続行する場合、観点 1 は「issue なし」として扱い、他の観点でレビューする。
- 作業ツリーの状態を確認する（`git status`）。未コミットの変更や未追跡ファイルも差分に含める。

### 2. 差分を取得する

```bash
base=$(git merge-base HEAD <base ブランチ>)
git diff --stat $base          # 変更ファイルの一覧（未コミット含む）
git diff $base                 # 差分本体
git log --oneline $base..HEAD  # コミット一覧
git status --short             # 未追跡ファイルの確認
```

- 変更ファイルは差分だけでなく**ファイル全体**を読む。変更箇所の呼び出し元・呼び出し先・関連テストも確認する。
- 差分が非常に大きい場合は、ファイル単位に分けて確認し、観点を落とさない。

### 3. 周回レビューをする

**周ごとの狙い**

| 周 | 狙い |
|----|------|
| 1 周目 | 7 観点すべてで、差分全体を確認する。テスト・lint・型チェックを実行する |
| 2 周目 | 1 周目の修正を検証し、修正後の差分全体を 7 観点で再確認する。修正が新たな問題を生んでいないか見る |
| 3 周目 | 先入観を外した通しレビュー。これまでの指摘ログを見ずに、変更ファイルを逆順に読み、初見のレビュアーとして 7 観点で確認する。その後でログと突き合わせる |
| 4〜5 周目 | 直前の周で新規の指摘があった場合のみ。直前の修正の検証と再確認 |

**各周のやり方**

1. 観点ごとに差分を読み直す（7 観点を同時に見ない）。
2. 観点ごとに、指摘と「確認したこと」を記録する（指摘なしの場合も確認した内容を書く）。
3. 指摘を下記の方針で処理する（修正、または人間への判断依頼）。
4. 修正後は、関連するテストと lint などを再実行する。

**終了条件**

- **最低 3 周は必ず行う**。1〜2 周目で指摘が 0 件でも、3 周目は省略しない。
- 3 周目以降、直近の周で「修正が必要な新規指摘」が 0 件であり、過去の修正がすべて検証済みなら終了する。
- 5 周に達しても新規指摘が出続ける場合は打ち切り、残りの指摘を報告する。

### 4. 指摘を処理する

**指摘の記録形式**

```
[R{周}-{連番}] {観点} / {重大度}
場所: path:行番号
問題: {何が問題か}
根拠: {なぜ問題と言えるか。再現手順・該当コード・issue の該当箇所}
対応: {修正した内容 / 修正案 / 判断依頼}
```

**重大度**

| 重大度 | 基準 |
|--------|------|
| blocker | 動作しない、データ損失、重大なセキュリティ問題、受け入れ条件の未達 |
| major | バグ、重要な経路のテスト不足、後方互換性の破壊 |
| minor | 保守性、軽微な不整合、小さなテスト不足 |
| nit | 好みの範囲、表記の揺れ |

**処理の方針**

- blocker / major: 必ず対応する。明確な欠陥は修正し、判断が必要なものは判断依頼にする。
- minor: 範囲内で自明なものは修正する。
- nit: 報告のみ。
- **自分で修正してよい**のは、issue のスコープ内で、正解が明確なもの。修正は作業ツリーに反映する（コミットと push はしない）。
- **修正せず人間に判断を求める**のは、仕様の解釈が分かれるもの、トレードオフがあるもの、スコープの拡大を伴うもの。選択肢と推奨案を添える。
- **issue 自体の誤りや不足**が見つかった場合は、コードで回避しない。issue を更新して `ready` に戻す必要があることを報告し、人間の判断を仰ぐ（AGENTS.md の規約に従う）。
- 差分の範囲外にある既存の問題は修正せず、「範囲外の気づき」として別に報告する。
- テストを通すためにテストを弱めたり削除したりしない。

### 5. 最終報告をする

```
## レビュー結果: {PR 可 / 要判断 / 要修正}

- 対象: {ブランチ} → {base}（issue: #NNNN）
- 実施: {N} 周
- 実行したチェック: {コマンドと結果}

### 指摘の集計
| 観点 | blocker | major | minor | nit |
（修正済み / 残り / 判断待ち がわかるようにする）

### 判断をお願いしたい点
1. {論点}: A / B（推奨: A。理由: …）

### 残っている指摘
{未対応の指摘とその理由。なければ「なし」}

### 範囲外の気づき
{なければ「なし」}

### 修正した内容
{主な修正の要約}
```

- 判定の基準: blocker / major が残っていなければ「PR 可」。判断待ちがあれば「要判断」。未修正の blocker / major があれば「要修正」。
- 修正を行った場合は、コミットが必要なことを伝え、コミットするかを確認する。
- 5 周で打ち切った場合は、その旨と残りの指摘を明記する。

## ルール

- PR を出す前、または push する前には、必ずこのスキルを実行する。
- 最低 3 周、最大 5 周。1 周で完了としない。
- 7 つの観点すべてを、毎周確認する。
- push、PR の作成、コミットはしない（コミットは agent-git に従い、ユーザーの確認後）。
- 指摘に根拠を付ける。推測は「推測」と明記する。
- 過去の周の結果を「確認済み」として信用せず、修正後の状態を再確認する。
- スコープ外の変更を勝手に行わない。
