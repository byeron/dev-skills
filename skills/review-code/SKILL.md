# review-code

**差分ではなく、メインブランチのコードそのもの**をレビューして、課題を洗い出すスキル。
洗い出した課題は、人間が選んだものを issue として起票する。その後は polish-issue で磨き上げる。

> ブランチの差分をレビューする場合は review-diff-code を使う。

> issue の管理方法（`issues/` の構造、ステータスの遷移、編集ルール）は `agent-issues` に従う。

## 基本方針

- **目的は課題の洗い出し**: 見つけた問題を、そのまま issue にできる形で整理する。修正はしない。
- **読み取り専用**: ソースコード・設定・テストは変更しない。変更・作成してよいのは、人間の確認後に起票する issue ファイルのみ。
- **検証した課題だけを報告する**: コード全体のレビューは誤検知が出やすい。報告の前に、コードを追って、またはコマンドで再現して確認する。確認できなかったものは「推測」と明記する。
- **issue 化できる粒度にする**: 1 つの課題 = 1 つの issue として修正できる単位にまとめる。同じ原因の指摘は 1 件にまとめ、巨大な課題は分割して提案する。
- **起票は人間の判断**: 起票するかどうかは人間が選ぶ。
- **件数を絞る**: 重要なものから順に並べ、起票候補は多くても 20 件程度に絞る。残りは「その他の気づき」にまとめる。

## 7 つの観点

| # | 観点 | 主な確認事項 |
|---|------|--------------|
| 1 | 仕様・ドキュメントとの整合 | README・ドキュメント・コメントと実装の食い違い、古くなった説明、未実装の機能の記載 |
| 2 | 正しさ・ロジック | バグ、境界値、null・空、エラー処理、例外経路、競合・並行性、型や単位の誤り |
| 3 | テスト | カバレッジの穴、重要経路の未テスト、不安定なテスト、実装を追認するだけのテスト |
| 4 | セキュリティ | 入力検証、認証・認可、インジェクション、秘密情報のハードコード、ログへの機密出力 |
| 5 | 設計・保守性 | 責務の分離、重複、複雑度、循環依存、既存規約との不一致、技術的負債 |
| 6 | 性能・信頼性・運用 | 計算量、N+1、リソースリーク、リトライ・タイムアウト、ログ・監視、設定の扱い |
| 7 | 依存関係・ビルド・開発環境 | 古い・脆弱な依存、未使用の依存、ビルドや CI の問題、再現性、開発環境の手順 |

観点を増やす場合は、この表に行を追加する。

## 手順

### 1. 対象を決める

- **ブランチ**: メインブランチ（AGENTS.md の規定、なければ `main` / `master`）を対象にする。現在のブランチが異なる場合は、チェックアウトを切り替えず、`git ls-tree -r <main>` と `git show <main>:<path>` で読む。切り替えや一時的なチェックアウトが必要な場合は、ユーザーに確認する。
- **範囲**: ユーザーがディレクトリ・モジュール・観点を指定していればそれに従う。指定がなければリポジトリ全体を対象にする。
- 範囲が大きい場合は、ディレクトリ構成から領域に分割し、レビュー計画を 2〜3 行で示してから進める。

### 2. コードベースを把握する

- README、AGENTS.md（または CLAUDE.md）、ドキュメント、ディレクトリ構成、言語・フレームワーク、ビルド・テストの方法を確認する。
- `issues/` の既存 issue を一覧にする（重複を避けるため）。
- 変更頻度の高いファイルや、過去の不具合修正が多い箇所を確認する（`git log --stat`、`git log --grep=fix`）。重点的に見る領域の手がかりになる。
- 既存のテスト・lint・型チェックを実行する。依存関係の脆弱性チェックは、ネットワークや追加のインストールが不要な範囲で行い、実行できなかった場合は報告に書く。

### 3. 領域ごとに、観点別にレビューする

- 領域ごとに、7 つの観点を順に確認する（観点を同時に見ない）。
- ファイルは断片ではなく全体を読み、呼び出し元・呼び出し先・関連テストも確認する。
- 領域 × 観点のカバレッジを記録する。確認できなかった領域・観点は、明示的に「未確認」とする。

### 4. 指摘を検証する

報告する前に、各指摘を次の方法で確認する。

- コードを追い、問題が実際に起こる条件を特定する。
- 可能なら、テストやコマンドで再現する。
- 呼び出し元の前提や、他の箇所での対処により、問題が実際には起きないことがないか確認する。
- 確認できなかったものは「推測」と明記する。

同じ原因の指摘はまとめる。

### 5. 既存 issue と照合する

- `open` / `needs-info` / `ready` / `approved` の issue と重複する指摘は、新規候補にせず、該当する issue 番号を示す。
- `done` / `discarded` の issue と同じ内容の指摘は、その経緯を確認する。破棄の理由が今も有効なら再掲しない。新たな根拠がある場合のみ、その旨を添えて候補にする。

### 6. 優先順位をつけて報告する

重大度、影響範囲、修正の容易さをもとに並べる。

**重大度**

| 重大度 | 基準 |
|--------|------|
| high | データ損失、セキュリティ上の重大な問題、広範囲に影響するバグ、主要機能の不具合 |
| medium | 限定的なバグ、重要な経路のテスト不足、放置すると悪化する技術的負債 |
| low | 軽微な不整合、小さな保守性の問題 |

**報告の形式**

```
## コードレビュー結果

- 対象: {ブランチ}（{コミットハッシュ短縮}）、範囲: {全体 / 指定した領域}
- 実行したチェック: {コマンドと結果。実行できなかったものはその理由}

### 起票候補（{N} 件）

| 仮ID | タイトル | 観点 | 重大度 | 種別 | 場所 |
|------|----------|------|--------|------|------|
| C-01 | … | 2 | high | bug | path:行番号 |

### 候補の詳細
**C-01 {タイトル}**
- 問題: {何が問題か}
- 根拠: {確認した事実。再現手順やコード。推測は明記}
- 影響: {何が起こるか}
- 修正の方向性: {1〜2 文。issue の「修正方針」の出発点になる程度}

### 既存の issue と重複するもの
{指摘 → issue 番号。なければ「なし」}

### その他の気づき
{起票に至らない小さな指摘。なければ「なし」}

### カバレッジ
| 領域 | 1 | 2 | 3 | 4 | 5 | 6 | 7 |
{確認済み ○ / 未確認 ×}

起票するものを選んでください（例: 「全て起票」「C-01, C-03 のみ」「high だけ」）。
```

### 7. 選ばれた指摘を issue として起票する

人間が選んだ指摘だけを起票する。起票しない場合や、確認の返答がない場合は、何も作成しない。

起票は、create-issue の手順と形式に従う。

- `issues/` に、連番とスラッグの付いたファイル名で作成する（既存の最大番号 + 1）。
- テンプレートを使い、ステータスは `open` とする。
- 種別は指摘の内容に応じて `bug` / `task` / `docs` などにする。
- 優先度は、high → high、medium → medium、low → low とする。
- 「概要」「背景・動機」「詳細」には、報告の「問題」「根拠」「影響」を転記する。根拠の `path:行番号` は残す。
- 「メモ」に、このレビューで見つけたことと、確認日を記録する。
- 磨き上げ（原因分析、実装手順、受け入れ条件の詳細化）は行わない。それは polish-issue の役割。

### 8. 完了を報告する

- 起票した issue の一覧（番号とタイトル）
- 起票しなかった候補の件数
- 次の手順の案内（polish-issue で磨き上げる、優先度の高いものから進める）

## ルール

- ソースコード・設定・テストは変更しない。作成してよいのは、人間が選んだ指摘の issue ファイルだけ。
- 検証していない指摘を、確定した課題として報告しない。
- 一般論や抽象的な助言（「テストを増やすべき」「リファクタリングすべき」など）だけの指摘はしない。具体的な場所と根拠を伴うものだけを挙げる。
- コードスタイルの好みの違いは、リポジトリの規約に反している場合を除き、指摘しない。
- 起票は人間の確認を経て行う。確認なしに issue を作らない。
- 既存の issue と重複して起票しない。
- 差分のレビューは行わない（review-diff-code の役割）。
